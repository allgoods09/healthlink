CHAPTER IV: METHODOLOGY

4.1 Requirements Analysis and Requirements Documentation

In describing how the project was designed, the developers used a use-case diagram and detailed use-case specifications to explain how HealthLink functions across its mobile and web platforms. The specifications are arranged according to the actual operational sequence: access control, BHW mobile and web field work, Secretary civil-registry administration, BNS nutrition services, PHN/MHO clinical care, and municipal administration.

Use Case Diagram Overview

HealthLink has six principal actors: Municipal Administrator, Municipal Health Officer (MHO), Public Health Nurse (PHN), Barangay Secretary, Barangay Nutrition Scholar (BNS), and Barangay Health Worker (BHW). BHW and BNS users may self-register. Secretaries approve and assign frontline users in their barangay, while the Municipal Administrator manages municipal roles and has supervisory access. The BHW mobile application uses SQLite for local-first field work and guarded manual synchronization. Protected web modules require an authenticated, email-verified, active, approved, and role-authorized account.

USE CASE SPECIFICATIONS

Use Case Name:	Self-Registration and Email Verification
ID:	UC-01
Importance Level:	High
Primary Actor:	Prospective BHW or BNS
Use Case Type:	Essential, Detailed
Scenario:	A prospective BHW or BNS creates an account and confirms ownership of the provided email address.
Brief Description:	This use case allows a frontline worker to submit personal and account details for review. Registration does not provide immediate system access because the email must first be verified and the account must later be approved by the appropriate Barangay Secretary.
Trigger:	The applicant opens and submits the public registration form.
Normal Flow of Events:
1. The applicant enters separate name fields, an email address, a password, the requested BHW or BNS role, and the barangay where the applicant will serve.
2. The applicant reviews and accepts the terms before submitting the form.
3. The system validates the required fields, requested role, password rules, and uniqueness of the email address.
4. The system creates an inactive account with approval_status=pending and registered_via=self.
5. The system sends a signed verification link to the registered email address.
6. The applicant opens the link, and the system records email_verified_at when the link is valid.
7. The system notifies the Barangay Secretary that a verified applicant is waiting for review.
Sub Flows:	If the first message is not received, the applicant may request another verification email. Password recovery is also available for an existing account.
Alternative/Exceptional Flows:	Public registration accepts only BHW and BNS roles. Duplicate emails, incomplete or invalid information, and expired or invalid verification links are rejected. The applicant cannot enter protected modules while the account remains unverified, pending, rejected, or inactive.

Use Case Name:	Frontline Account Approval and Assignment
ID:	UC-02
Importance Level:	High
Primary Actor:	Barangay Secretary
Use Case Type:	Essential, Detailed
Scenario:	A Barangay Secretary reviews a verified BHW or BNS applicant who requested assignment to the Secretary's barangay.
Brief Description:	This use case confirms whether a frontline applicant is authorized to work in the barangay. It also establishes the geographic assignment that will control which records and functions the user can access.
Trigger:	A verified registration appears in the pending section of the Frontline Team module.
Normal Flow of Events:
1. The Secretary opens the pending applicant and reviews the submitted identity, requested role, email-verification state, and barangay.
2. The Secretary confirms that the applicant belongs to the barangay and that the requested frontline role is appropriate.
3. For a BHW applicant, the Secretary selects an active purok assignment. For a BNS applicant, the system applies barangay-level scope.
4. The Secretary confirms the approval decision.
5. The system records the approving user and time, saves the assignment, changes the approval status, and activates the account.
6. The system writes an audit entry and informs the applicant that the account has been approved.
Sub Flows:	The Secretary may create a frontline account directly, update an existing assignment, resend or mark email verification, and reset or generate a password when authorized.
Alternative/Exceptional Flows:	The system blocks cross-barangay account management and does not approve a BHW without a valid active purok. If the application is rejected, the system retains the reviewer, decision time, and review notes and leaves the account without protected access.

Use Case Name:	Web Authentication, Recovery, and Profile Management
ID:	UC-03
Importance Level:	High
Primary Actor:	Registered User
Use Case Type:	Essential, Detailed
Scenario:	A registered user signs in to the web application and manages basic account information during an authorized session.
Brief Description:	This use case authenticates the user, checks whether the account is permitted to enter the system, and directs the user to the dashboard for the assigned role. It also covers profile updates, password changes, and secure logout.
Trigger:	The user submits the login form or opens an available account-management action.
Normal Flow of Events:
1. The user enters the registered email address and password.
2. The system validates the credentials and checks email verification, approval, activation, and role status.
3. After successful authentication, the system regenerates the session to protect it from reuse.
4. The system identifies the user's role and redirects the user to the corresponding authorized dashboard.
5. During the session, the user may update permitted profile fields or change the account password after passing validation.
6. When the user logs out, the system invalidates the session and returns the browser to a public page.
Sub Flows:	A user who forgets the password may request a branded reset link. An unverified user may resume the email-verification process instead of attempting protected access.
Alternative/Exceptional Flows:	The system denies access when credentials are incorrect or the account is unverified, pending, rejected, or inactive. After logout, no-cache protection prevents a protected page from being reopened through normal browser history.

Use Case Name:	Role-Based Notification Review
ID:	UC-04
Importance Level:	Medium
Primary Actor:	Authenticated User
Use Case Type:	Essential, Detailed
Scenario:	An event in HealthLink requires one or more authorized users to be informed or to take action.
Brief Description:	This use case creates notifications according to the recipient's role and assigned scope. Each notification gives enough context for the user to understand the event and, when applicable, links to the related record.
Trigger:	A registration, draft, correction, triage, escalation, PhilPEN alert, registry creation, or mobile-release event is recorded.
Normal Flow of Events:
1. The system identifies the event type and determines which roles and geographic assignments should receive it.
2. The system confirms that each intended recipient is eligible to receive information about the affected record.
3. A notification is stored with its title, message, severity level, category, action URL, sender, and supporting metadata.
4. The recipient sees the updated unread count and opens the notification list.
5. The system marks the selected notification as read when it is opened.
6. If an action link is available, the system rechecks authorization before displaying the related record.
Sub Flows:	A user may mark all accessible notifications as read. Through the mobile API, a BHW receives only notifications belonging to the authenticated account.
Alternative/Exceptional Flows:	If no eligible recipient exists, the system does not create a message. Possession of a notification link does not bypass role or location-based authorization.

Use Case Name:	BHW Mobile Login and Single-Device Access
ID:	UC-05
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	An approved and assigned BHW signs in to the HealthLink Android application from a field device.
Brief Description:	This use case verifies that the account is eligible for mobile access and creates one active authenticated mobile session. The saved assignment determines the barangay and purok available to the BHW during field work.
Trigger:	The BHW submits an email address, password, and available device information on the mobile login screen.
Normal Flow of Events:
1. The application sends the credentials and device details to the mobile authentication endpoint.
2. The server checks whether the installed release may connect and whether mobile login is under maintenance.
3. The server validates the credentials, BHW role, verified email, approved and active account state, barangay, and active purok assignment.
4. After validation, the server revokes older mobile tokens belonging to the account to enforce single-device access.
5. The server issues a new Sanctum token and records relevant device, application-version, and locale information in the audit trail.
6. The application stores the authenticated identity and assignment for use in the local-first workspace.
Sub Flows:	The BHW may request password recovery from the mobile application. Logging out revokes the current token and removes access to the authenticated session.
Alternative/Exceptional Flows:	Login is denied for a non-BHW user or an account that is unassigned, inactive, unverified, pending, rejected, rate-limited, or blocked by maintenance settings.

Use Case Name:	First-Time Mobile Bootstrap
ID:	UC-06
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	A BHW has successfully logged in on a new or cleared installation that does not yet contain an offline barangay registry.
Brief Description:	This use case prepares the device for local-first field work by downloading the BHW's authorized dataset and storing it safely in SQLite. Data-entry features remain unavailable until the initial local copy is complete.
Trigger:	The application detects that bootstrapCompleted is false after authentication.
Normal Flow of Events:
1. The application displays the Initial Sync screen instead of opening an incomplete field workspace.
2. Using the authenticated token, the application requests the bootstrap dataset from the server.
3. The server validates the session and limits the requested information to the BHW's assigned barangay.
4. The server returns assignment details together with authorized households, residents, visits, and PhilPEN assessments.
5. The application writes the returned dataset to SQLite as a transaction so that a partial write is not treated as a valid registry.
6. After a successful transaction, the application stores bootstrap completion and last-sync information.
7. The BHW is taken to the local-first workspace and may begin using the downloaded records.
Sub Flows:	On later launches, the application can open the SQLite dataset immediately. If a different BHW signs in, the previous account's local dataset is cleared before the new account is prepared.
Alternative/Exceptional Flows:	A connection failure, server error, invalid token, or download-maintenance state keeps the workspace blocked and presents Retry and Log out actions. Incomplete data is not marked as a successful bootstrap.

Use Case Name:	Offline Barangay Directory and Mobile Registry Capture
ID:	UC-07
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	While working in the field, a BHW searches the barangay directory or records household and resident information without relying on a continuous internet connection.
Brief Description:	This use case provides read access to the downloaded barangay directory while limiting mobile creation and editing to the BHW's assigned purok. New or changed records remain local until they are accepted during synchronization.
Trigger:	The BHW opens the Directory or starts an available household or resident form.
Normal Flow of Events:
1. The application loads household and resident information from SQLite and allows the BHW to search the local directory.
2. Records from the whole assigned barangay may be viewed, including full read-only details for residents of other puroks.
3. When the selected record belongs to the BHW's assigned purok, the application enables the permitted create or edit action.
4. The BHW enters the household location, identity, relationship, and other required civil information.
5. The application validates the fields and generates a UUID that can identify the record during later synchronization.
6. The record is saved locally with sync_status=pending_upload and remains available even when the device is offline.
7. The BHW may correct the pending local record until the server accepts it during synchronization.
Alternative/Exceptional Flows:	The application does not offer editing for another purok, and the server rejects duplicate or out-of-scope submissions. Accepted mobile entries are written directly to Household or Resident and the Secretary is notified; they do not enter the separate web draft tables.

Use Case Name:	Offline Household Visit Capture
ID:	UC-08
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	A BHW documents a household visit conducted within the assigned purok, including notes and available photographic evidence.
Brief Description:	This use case stores a field visit on the device for later synchronization. It preserves when the visit occurred, what the BHW observed, and any optional photographs selected from the camera or gallery.
Trigger:	The BHW selects the visit action from an authorized household record.
Normal Flow of Events:
1. The application loads the chosen household from SQLite and verifies that it belongs to the BHW's assigned purok.
2. The BHW enters the visit date and time and writes relevant field notes.
3. The BHW may capture photographs or select them from the gallery and may remove unwanted selections before saving.
4. The application validates the visit information and generates a mobile_uuid for retry-safe synchronization.
5. The visit is stored locally as pending_upload and remains visible in the offline workspace.
6. During synchronization, the server validates the assignment, stores valid photographs, records source=mobile and last_synced_at, and returns the accepted record.
7. The application reconciles the server result and marks the local visit as synced.
Sub Flows:	A visit may be saved without photographs. The BHW may edit it while it is still unsynced.
Alternative/Exceptional Flows:	Visits for another purok and invalid retained photographs are rejected. If upload or file storage fails, the local visit remains pending rather than being discarded. The current web routes do not provide a dedicated household-visit module for the Secretary or BNS.

Use Case Name:	Offline PhilPEN Risk Assessment
ID:	UC-09
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	A BHW conducts a Revised 2022 PhilPEN risk assessment for an adult resident during field work.
Brief Description:	This use case records the resident's measurements, relevant history, risk factors, screening results, and follow-up information. It also identifies findings that require timely referral while keeping clinical prescribing outside the BHW role.
Trigger:	The BHW selects New Risk Assessment from an eligible resident's record.
Normal Flow of Events:
1. The application checks the resident's age on the assessment date and requires the resident to be at least 20 years old.
2. The application fills in the available resident identity and location details from the local registry.
3. The BHW completes the applicable PhilPEN sections, including measurements, medical and family history, risk factors, screening responses, reported medicines, advice, follow-up, and remarks.
4. The application validates the entries, calculates the BMI, and determines whether the recorded findings raise a referral flag.
5. The application generates a mobile_uuid and stores the assessment locally as pending_upload.
6. During synchronization, the server validates and accepts the assessment and sends relevant alerts for critical findings.
7. The accepted assessment becomes read-only on the device to preserve the historical screening record.
Sub Flows:	The adult directory may be filtered by assessment recency, and the BHW may deliberately begin a new assessment when reassessment is appropriate.
Alternative/Exceptional Flows:	The system blocks assessment of an underage resident. Critical red flags produce an immediate referral warning and notify the PHN or MHO after synchronization. A synced historical assessment cannot be edited, and the workflow does not permit the BHW to prescribe medicine.

Use Case Name:	Guarded Manual Mobile Synchronization
ID:	UC-10
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	A BHW intentionally synchronizes locally stored field records and then refreshes the device with the latest authorized barangay data.
Brief Description:	This use case protects unsent work by uploading pending records before replacing local reference data. A fresh download is allowed only after the device has no unresolved local changes.
Trigger:	The BHW selects Sync Now from the mobile application.
Normal Flow of Events:
1. The application checks network availability and counts household, resident, visit, and assessment rows that have not been synchronized.
2. Pending records are grouped into an upload request with their local IDs and mobile_uuid values.
3. The server validates the token, payload size, required fields, record relationships, and barangay or purok scope.
4. For repeated requests, the server uses the model ID or UUID to reconcile the submission without creating an unintended duplicate.
5. The server records the attempt through SyncLog and AuditLog and returns the result for each submitted record.
6. The application saves returned server IDs and marks only accepted rows as synced.
7. When no pending rows remain, the application downloads a fresh scoped bootstrap dataset and updates its last-sync state.
Alternative/Exceptional Flows:	A synchronization attempt may be successful, partially successful, or failed, and the device may submit a failure report for administrative review. If uploading fails, the download stage is skipped and the existing local cache is preserved. Rejected rows remain pending for correction or retry. Maintenance settings and oversized payloads produce controlled errors instead of clearing local work.

Use Case Name:	BHW Web Field Draft Package
ID:	UC-11
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	A BHW uses the web application to propose a new household together with its resident members for official verification.
Brief Description:	This use case creates a linked HouseholdDraft and one or more ResidentDraft records. The package remains separate from the verified civil registry until the Barangay Secretary reviews and approves it.
Trigger:	The BHW selects New Draft Package from the web field-work module.
Normal Flow of Events:
1. The BHW selects a purok allowed by the account assignment.
2. The BHW enters the proposed household location, classification, and applicable risk information.
3. The BHW adds the available resident details and links each resident draft to the proposed household.
4. The system validates the package and saves the household and resident drafts together.
5. While the package remains pending, the BHW reviews the information and corrects incomplete or inaccurate entries.
6. The BHW submits the completed package for verification.
7. The system records the submission, creates an audit entry, and notifies the Barangay Secretary.
Sub Flows:	The BHW may monitor the package after submission and view whether it remains pending or has been approved or rejected.
Alternative/Exceptional Flows:	The system rejects an out-of-scope purok and does not allow an already reviewed package to be edited. A rejected package remains available with the Secretary's review notes.

Use Case Name:	Verified Profile Correction Request
ID:	UC-12
Importance Level:	High
Primary Actor:	BHW or PHN
Use Case Type:	Essential, Detailed
Scenario:	A BHW or PHN notices that verified household or resident information is inaccurate but does not have authority to alter the civil registry directly.
Brief Description:	This use case allows an authorized field or clinical user to propose a correction and explain why it is needed. The existing verified record remains unchanged until the Barangay Secretary decides on the request.
Trigger:	The BHW or PHN opens the correction-request form for an accessible verified record.
Normal Flow of Events:
1. The user selects a household or resident within the account's authorized scope.
2. The system displays the current verified values so the user can identify the inaccurate information.
3. The user enters only the proposed changes and provides a reason that will help the Secretary evaluate the request.
4. The system validates that the request contains a meaningful change and creates a pending ProfileUpdateRequest.
5. The system links the request to the subject and requester, records the submission, and notifies the Barangay Secretary.
6. The requester may later view the resulting approval or rejection and the corresponding decision information.
Alternative/Exceptional Flows:	An empty request or a subject outside the user's scope is rejected. Submission alone never changes the verified civil record; changes are applied only after approval.

Use Case Name:	BHW Clinic Triage Submission
ID:	UC-13
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	A BHW records a resident's available pre-consultation vital signs and submits them for assessment by a municipal PHN.
Brief Description:	This use case creates a pending triage record that carries basic observations from the barangay into the clinical queue. The record may be corrected before use, but it becomes fixed once incorporated into a clinical encounter.
Trigger:	The BHW selects New Triage Entry from the web application.
Normal Flow of Events:
1. The BHW searches for and selects an active resident from the assigned barangay.
2. The system displays the resident's identifying context to reduce the chance of recording information for the wrong person.
3. The BHW enters the triage time, blood pressure, heart rate, temperature, respiratory rate, glucose when available, and relevant notes.
4. After validation, the system creates a pending TriageRecord linked to the resident and submitting BHW.
5. The system records the action in the audit trail and notifies the PHN that a triage record is waiting.
6. The BHW may edit the entry while consumed_at remains empty.
7. When a PHN uses the triage in an encounter, the system records the consumer, consumption time, and resulting status.
Alternative/Exceptional Flows:	The system rejects a resident outside the BHW's authorized scope. Once consumed by an encounter, the triage record is permanently locked against BHW editing so the clinical record remains consistent.

Use Case Name:	Child Nutrition Assessment Referral
ID:	UC-14
Importance Level:	High
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	During community work, a BHW identifies a child who should receive a formal nutrition assessment from the BNS.
Brief Description:	This use case creates an open nutrition referral with the BHW's stated reason. The referral remains visible to the BNS until an official OPT+ measurement is recorded and linked as its resolution.
Trigger:	The BHW selects Flag for Nutrition Assessment for an eligible child.
Normal Flow of Events:
1. The BHW selects an eligible child from the accessible resident records.
2. The system displays the child's identity and household context for confirmation.
3. The BHW records the reason for requesting assessment and submits the referral.
4. The system creates an open flag with the submitting BHW, time, and barangay scope.
5. The system notifies the assigned BNS and displays the child among open referrals on the BNS dashboard.
6. When the BNS records the corresponding official OPT+ measurement, the system stores the resolver and measurement, records closed_at, and changes the referral to closed.
Sub Flows:	The BHW may review the referral later to see whether it is still open or has already been resolved.
Alternative/Exceptional Flows:	The system may block another open referral for the same child when one already requires action. This referral action does not authorize the BHW to enter an official OPT+ measurement.

Use Case Name:	BHW Community Campaign Task Completion
ID:	UC-15
Importance Level:	Medium
Primary Actor:	BHW
Use Case Type:	Essential, Detailed
Scenario:	A BHW carries out a campaign task that has been assigned to a particular resident or household.
Brief Description:	This use case lets the BHW document whether an assigned field task is still pending, completed, or skipped and retain notes explaining what occurred during the activity.
Trigger:	The BHW opens an assigned entry from the campaign roster or dashboard.
Normal Flow of Events:
1. The system lists campaign assignments belonging to the authenticated BHW.
2. The BHW opens an entry and reviews the campaign details and intended resident or household target.
3. After performing or attempting the task, the BHW selects the appropriate pending, completed, or skipped status.
4. The BHW enters relevant notes and submits the update.
5. For a completed or skipped task, the system records completed_at together with the selected status.
6. The system saves the change and creates an audit entry identifying the user and updated assignment.
Alternative/Exceptional Flows:	A BHW cannot open or update another worker's assignment. Current routes support viewing and processing assigned tasks but do not expose campaign-definition or assignment-creation pages.

Use Case Name:	Secretary Civil Registry and Household Clustering
ID:	UC-16
Importance Level:	High
Primary Actor:	Barangay Secretary
Use Case Type:	Essential, Detailed
Scenario:	The Barangay Secretary creates and maintains the official household and resident records for the assigned barangay.
Brief Description:	This use case covers the continuing administration of civil-registry information, including household location and risk data, resident identity and socioeconomic details, household-head designation, relocation, and record status.
Trigger:	The Secretary opens the Household or Resident module and chooses a permitted record-management action.
Normal Flow of Events:
1. The Secretary selects an active purok and, when working with a resident, the appropriate household within the assigned barangay.
2. The Secretary enters or updates the available household, civil, relationship, and socioeconomic information.
3. The system validates the barangay scope, PhilSys and identity fields, required values, and relationships between records.
4. For a new record, the system generates the proper official identifier; for an update, the existing identifier is preserved.
5. The Secretary designates a household head when an eligible resident is available and reviews the resulting household membership.
6. The system saves the verified information and records the responsible user and changes in the audit trail.
Sub Flows:	The Secretary may relocate a resident to a new or existing household, change a resident's lifecycle state to active, deceased, or relocated, activate or deactivate permitted records, and generate an RBI profile PDF or print view.
Alternative/Exceptional Flows:	Secretary routes do not hard-delete official records. Cross-barangay changes, invalid relocation destinations, and inconsistent relationships are rejected, while serious status or location changes require confirmation.

Use Case Name:	Secretary Purok and Frontline Team Management
ID:	UC-17
Importance Level:	High
Primary Actor:	Barangay Secretary
Use Case Type:	Essential, Detailed
Scenario:	The Barangay Secretary maintains the puroks and frontline personnel responsible for service delivery in the assigned barangay.
Brief Description:	This use case combines local geographic maintenance with the administration of BHW and BNS accounts. It ensures that frontline users have valid roles, account states, and work assignments.
Trigger:	The Secretary opens the Puroks or Frontline Team module.
Normal Flow of Events:
1. The Secretary reviews existing puroks and may create, update, activate, or deactivate a purok within the assigned barangay.
2. The Secretary opens the scoped frontline list to review BHW and BNS users, pending applications, and current assignments.
3. The Secretary creates or updates an authorized frontline account and verifies the role and contact information.
4. The Secretary assigns a BHW to a valid active purok or confirms barangay scope for a BNS.
5. When authorized, the Secretary manages verification state or performs an available password action for the account.
6. The system validates and saves each change and records it in the audit trail.
Alternative/Exceptional Flows:	The system rejects a duplicate purok number, cross-barangay data, a non-frontline role, or an assignment that does not match the user's role and barangay.

Use Case Name:	Secretary Draft and Correction Verification
ID:	UC-18
Importance Level:	High
Primary Actor:	Barangay Secretary
Use Case Type:	Essential, Detailed
Scenario:	The Barangay Secretary examines a household draft package or profile-correction request submitted by an authorized field or clinical user.
Brief Description:	This use case allows the Secretary to verify proposed information, make justified corrections before approval, and either approve or reject the request. The original request and decision are retained as evidence of the review.
Trigger:	A pending HouseholdDraft package or ProfileUpdateRequest appears in the Secretary's review queue.
Normal Flow of Events:
1. The Secretary opens the pending item, and the system verifies that it belongs to the assigned barangay.
2. For a draft, the Secretary reviews the proposed household and linked residents. For a correction, the Secretary compares the current and proposed values.
3. The Secretary corrects the proposal when permitted and checks that required identity, location, and relationship information is valid.
4. The Secretary chooses approval or rejection, enters applicable review notes, and confirms the decision.
5. On approval, a transaction creates the verified household package or applies the accepted correction without leaving partial changes.
6. The system stores the reviewer, decision time, status, and notes and preserves the reviewed request.
7. The system adds an audit entry and notifies the requester of the result.
Sub Flows:	Approving a draft creates one verified household and all linked residents together. The Secretary may select an eligible proposed resident as the household head.
Alternative/Exceptional Flows:	A rejection requires a reason and does not change verified registry data. An out-of-scope or already reviewed request cannot be processed again.

Use Case Name:	Barangay Certificate Issuance
ID:	UC-19
Importance Level:	Medium
Primary Actor:	Barangay Secretary
Use Case Type:	Essential, Detailed
Scenario:	The Barangay Secretary issues a Barangay Clearance or Certificate of Indigency to an eligible resident or household.
Brief Description:	This use case creates a uniquely numbered certificate, generates its PDF, and records the transaction in a searchable issuance log for later reference.
Trigger:	The Secretary selects Issue Certificate from the certificate module.
Normal Flow of Events:
1. The Secretary selects the certificate type and indicates whether the recipient is a resident or household.
2. The Secretary searches for and selects an active recipient within the assigned barangay.
3. The system displays the recipient information, and the Secretary enters the purpose, issue date, and any permitted remarks.
4. After validation, the system generates the next certificate number using the certificate type, barangay, year, and sequence.
5. The system stores the certificate details, issuing Secretary, and issuance time and records the action in the audit trail.
6. The Secretary views the completed certificate and may download its generated PDF for printing or release.
Sub Flows:	The Secretary may search and filter the certificate log and export the permitted results as CSV, XLSX, or PDF.
Alternative/Exceptional Flows:	The system rejects an out-of-scope or inactive recipient, an invalid certificate-recipient pairing, or a request missing required issuance information.

Use Case Name:	RBI Document and Demographic Report Generation
ID:	UC-20
Importance Level:	High
Primary Actor:	Barangay Secretary
Use Case Type:	Essential, Detailed
Scenario:	The Barangay Secretary prepares an official Registry of Barangay Inhabitants document or a filtered demographic report.
Brief Description:	This use case converts verified barangay records into template-based RBI PDFs or tabular demographic exports. It limits output to the Secretary's assigned barangay and records the export for accountability.
Trigger:	The Secretary requests an output from the Documents or Demographic reporting module.
Normal Flow of Events:
1. The Secretary selects RBI Form A, RBI Form B, or an available demographic report.
2. The Secretary applies the supported filters and chooses an allowed output format.
3. The system validates the request and retrieves matching verified records only from the assigned barangay.
4. For an RBI document, the system imports the immutable PDF template and overlays the required information as vector text.
5. When Form A contains more household members than one page can hold, the system repeats the member page and places the attestation only on the final page.
6. The system inserts the configured official information where required and produces the requested PDF, CSV, or XLSX file.
7. The file is returned to the Secretary, and the export event is added to the audit trail.
Alternative/Exceptional Flows:	If no records match the request or the selected format is unsupported, the system does not create a misleading or invalid output file.

Use Case Name:	BNS OPT+ Campaign and Growth Assessment
ID:	UC-21
Importance Level:	High
Primary Actor:	BNS
Use Case Type:	Essential, Detailed
Scenario:	A BNS records the growth measurements of an eligible child during an authorized OPT+ campaign period.
Brief Description:	This use case preserves each measurement as part of the child's nutrition history and derives applicable status classifications from the available WHO references. The latest result also supports the BNS watchlist and may resolve an open BHW referral.
Trigger:	The BNS selects Record Measurement within an OPT+ campaign.
Normal Flow of Events:
1. The BNS creates or selects an OPT+ period belonging to the assigned barangay.
2. The BNS searches for and selects a verified child who is eligible for measurement in that period.
3. The BNS records the measurement date, weight, height or length, measurement posture, and relevant remarks.
4. The system validates the values, calculates the child's age in months, and retrieves the applicable reference coverage.
5. The system calculates the supported weight-for-age, height-for-age, and weight-for-length or height z-scores and corresponding statuses.
6. A new OptMeasurement is stored without replacing the child's earlier measurement history.
7. The system updates the latest-status watchlist and closes a matching open BHW referral by linking it to the measurement.
8. The BNS may include the authorized campaign results in an audited CSV, XLSX, or PDF export.
Sub Flows:	The BNS may update permitted campaign details or status. Watchlist decisions use the child's latest available measurement while prior measurements remain in history.
Alternative/Exceptional Flows:	The system rejects a duplicate child-campaign-date entry, an age outside 0-71 months, multiple active periods of the same type, or a measurement for which reference coverage is unavailable. It does not guess a nutrition classification.

Use Case Name:	BNS Feeding Program Management
ID:	UC-22
Importance Level:	High
Primary Actor:	BNS
Use Case Type:	Essential, Detailed
Scenario:	A BNS organizes a supplementary feeding program and monitors each enrolled child's participation and progress over time.
Brief Description:	This use case connects a scoped feeding program with verified child records, attendance entries, and recurring progress observations. Historical entries remain available so changes can be reviewed across the program period.
Trigger:	The BNS creates a feeding program or opens an existing program in the assigned barangay.
Normal Flow of Events:
1. The BNS records the program name, schedule, scope, status, and other required program details.
2. The BNS selects an eligible verified child from the nutrition watchlist or through the permitted manual enrollment process.
3. The system validates the child and creates an enrollment linked to the program.
4. On feeding dates, the BNS records the child's attendance according to the available attendance options.
5. At appropriate intervals, the BNS adds weight or progress information and notes relevant observations.
6. The BNS updates the enrollment or program status as participation and implementation change.
7. The system preserves earlier attendance and progress entries rather than replacing the program history.
Sub Flows:	A borderline child or another child found eligible during field work may be enrolled manually after the BNS confirms the verified resident and program scope.
Alternative/Exceptional Flows:	The system rejects a child from another barangay and any enrollment, attendance, or progress entry that is incomplete, inconsistent, or unrelated to the selected program.

Use Case Name:	Maternal, Infant Feeding, and Micronutrient Surveillance
ID:	UC-23
Importance Level:	High
Primary Actor:	BNS
Use Case Type:	Essential, Detailed
Scenario:	A BNS monitors maternal nutrition, infant-feeding practices, and micronutrient distribution for verified residents of the assigned barangay.
Brief Description:	This use case maintains nutrition-specific profiles and dated observations without giving the BNS authority to modify civil-registry information. Current status and historical events are kept separately so earlier records remain traceable.
Trigger:	The BNS opens the Maternal Tracking or Micronutrients module and selects an available recording action.

1. The BNS searches for and selects a verified resident within the assigned barangay.
2. The system displays identifying civil information as read-only context.

Use Case Name:	PHN Triage Consumption and Clinical Encounter
ID:	UC-24
Importance Level:	High
Primary Actor:	PHN
Use Case Type:	Essential, Detailed
Scenario:	A PHN conducts a consultation using a pending BHW triage record or creates an encounter for a municipal walk-in patient.
Brief Description:	This use case brings relevant community and nutrition information into the clinical workflow and records the PHN's assessment, action, disposition, treatment notes, follow-up plan, and any need for MHO review.
Trigger:	The PHN opens an unconsumed triage entry or selects New Walk-In Encounter.

Alternative/Exceptional Flows:	A consumed triage record cannot be reused, and an invalid resident or triage selection is rejected. The PHN may view civil information for clinical context but cannot directly edit the verified civil profile.

Use Case Name:	MHO Escalation Review and Resolution
ID:	UC-25
Importance Level:	High
Primary Actor:	MHO
Use Case Type:	Essential, Detailed
Scenario:	The MHO evaluates a clinical encounter that a PHN has formally escalated for higher-level review and disposition.
Brief Description:	This use case records the MHO's final assessment and any applicable override, prescription, referral, disposition, instructions, resolution, and follow-up. One review remains linked to the encounter so later updates do not create conflicting decisions.
Trigger:	An encounter with is_escalated_to_mho=true appears in the MHO escalation queue.
Normal Flow of Events:
1. The MHO opens an escalated encounter from the authorized queue.
2. The system presents the resident context, originating triage, PHN assessment, nutrition information, and available clinical history.
3. After evaluation, the MHO records the applicable decision fields, including final assessment and any prescription, referral, override, disposition, or instructions.
4. The MHO specifies required follow-up and whether the escalation can be considered resolved or closed.
5. The system validates the decision and creates the encounter's MhoClinicalReview, or updates that same review when one already exists.
6. The system synchronizes the resulting review and resolution state with the encounter.
7. The action is audited, and the responsible PHN is notified of the MHO's decision.
Alternative/Exceptional Flows:	An encounter that was not escalated cannot receive an MHO review through this process. An existing review is updated rather than duplicated, and access is denied to an unauthorized user.

ID:	UC-26
Importance Level:	High

Use Case Type:	Essential, Detailed
Scenario:	The Municipal Administrator reviews municipality-wide activity, prepares reports, and performs authorized supervisory maintenance when intervention is required.
Brief Description:	This use case provides a command-center view of field, registry, nutrition, and clinical operations across barangays. Most operational information is used for oversight, while administrative create, update, archive, or restore actions remain controlled and auditable.

Use Case Name:	Administrative Security, Mobile Operations, and Recovery
ID:	UC-27
Importance Level:	High

Use Case Type:	Essential, Detailed

IMPLEMENTATION ACCURACY NOTES

1. sync_status and pending_upload are SQLite states. The server uses mobile_uuid, model IDs, last_synced_at, SyncLog, AuditLog, created_at, and updated_at.
2. BHW web intake uses HouseholdDraft and ResidentDraft with Secretary approval. Current mobile household/resident synchronization writes directly to Household and Resident after validation.
3. Mobile household visits are stored and synchronized, but the current web route file does not expose a dedicated Secretary or BNS Household Visits module.
4. BHW campaign assignments can be viewed and updated, but the current route file does not expose campaign-definition or assignment-creation pages.
5. BNS write access is confined to nutrition records; broad civil CRUD, team, device, and sync administration remain unavailable.
